### 场景 4：乱码行

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入 `qwertyuiop` 或 `@@@乱码@@@` 等无法识别为 `<a,b>` 格式、且不以 `#` 开头的文本行 |
| **程序应表现** | 弹窗提示："第X行：格式错误：缺少左括号 '<'" |
| **处理方案** | `InputValidator` 校验阶段拦截；当一行完全不存在左尖括号，统一报缺少左括号，不再细分其他错误 |
| **备注** | 以 `#` 开头的行会被当作注释静默跳过，不作为乱码行处理 |

### 场景 5：重复边

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入了两条或多条相同的边，如 `<a,b>` 出现两次 |
| **程序应表现** | 第一条正常解析；第二条产生警告"重复的关系 <a,b>，已忽略"；图中只保留一条边，入度不重复增加 |
| **处理方案** | DataParser 通过 `Graph.addEdge` 返回 false 识别重复，产生 warning；InputValidator 通过 `seenEdges` 集合检测重复，产生 warning；两者的 warning 消息字符串完全一致：`"重复的关系 <" + from + "," + to + ">，已忽略"`；B 的状态栏可选择性显示警告数 |

---

### 场景 6：自环（顶点指向自身）

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入 `<a,a>` 这样的自环边 |
| **程序应表现** | 正常解析并加入图，不报错也不产生警告；环检测模块返回环路径 `[a, a]`；B 弹窗提示"检测到环路: a → a"；C 的绘图高亮自环边 |
| **处理方案** | DataParser 识别到自环边并保留入图，直接调用 `Graph.addEdge` 保留；环路路径识别由 CycleDetector 模块完成；Graph 正常记录自环（入度 +1，出度 +1）；拓扑排序算法不能忽略自环，Kahn 算法因入度 > 0 无法消除自环节点，最终检测到环 |

---

### 场景 7：含环图（存在循环依赖）

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入的关系构成循环，如 `<a,b>` `<b,c>` `<c,a>` |
| **程序应表现** | 弹窗提示："检测到环路: a → b → c → a，无法完成拓扑排序"；关系图中环路径上的边和节点红色高亮 |
| **处理方案** | `CycleDetector` 使用 Kahn 计数法（出队数 < 顶点数）判定有环；DFS 三色标记定位具体环路径；结果面板清空或显示"含环，无有效拓扑序列" |

---

### 场景 8：空数据（无任何输入）

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户点击"计算"按钮时输入框为空 |
| **程序应表现** | B 的 UI 层检测到空图后弹出提示"没有有效数据，请输入至少一条关系"；不启动算法计算 |
| **处理方案** | 空输入由 UI 层（B）判断并提示，不由 InputValidator 或 DataParser 报错；`InputValidator.validate(null)` 返回 `isValid=true`、错误数 0；`DataParser.parse(null)` 返回空图、无错误 |
| **职责边界** | InputValidator 仅执行语法格式校验；输入为空或没有任何有效关系不属于格式错误，不会生成 error；空数据的业务提示弹窗由上层 UI 模块（B）完成 |

---

### 场景 9：全部孤立节点（无边）

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入的顶点之间没有任何先修关系，或输入为空图 |
| **程序应表现** | 正常显示所有节点（无边连接）；或空图时由 UI 层提示"没有有效数据" |
| **处理方案** | 当前 `<a,b>` 关系语法无法表达孤立节点，无有效边输入会返回无错误空图，空图业务提示交由 UI 层 B 实现；Graph 通过 `addVertex` 保存孤立节点；Kahn 算法对空图或全孤立点图返回所有顶点的任意排列 |

### 场景 10：大图（千节点规模）

| 项目 | 内容 |

### 场景 11：超长结果（拓扑序列数量极大）

| 项目 | 内容 |
|---|---|

### 场景 21：名称包含 Unicode 行分隔符

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入 `<A\u2028B,C>`、`<\u2028A,B>`、`<A,\u2028B>`、`<A\u0085B,C>`、`<A\u2029B,C>` 等名称中含 Unicode 行分隔符的行 |
| **程序应表现** | 弹窗提示："第X行：起点名称包含非法字符：XXX" 或 "第X行：终点名称包含非法字符：XXX" |
| **处理方案** | `DataParser` 和 `InputValidator` 的 `extractPair` 中，**不提前 `strip()` 括号内容**；提取 `fromRaw`、`toRaw` 后**先调用 `containsFormatDelimiter` 检查非法字符**（`\u0085`、`\u2028`、`\u2029` 等），**再 `strip()` 去除首尾空白**，**最后判断是否为空**。这样首尾和中间的 Unicode 行分隔符都能被拒绝，与 `model.Vertex.normalizeName` 规则保持一致 |
| **备注** | 若提前 `strip()` 括号内容，首尾的 `\u2028`、`\u2029`、`\u0085` 会被当作空白清掉，导致非法字符漏检；因此必须先检查非法字符，再 `strip()` |

### 场景 22：Graph 名称校验兜底异常

| 项目 | 内容 |
|---|---|
| **触发条件** | 即使 `containsFormatDelimiter` 漏检，或 A 的 `Vertex` 名称规则以后发生变化，`graph.addEdge` 抛 `IllegalArgumentException` |
| **程序应表现** | 弹窗提示："第X行：名称不符合图结构规则：XXX" |
| **处理方案** | `DataParser.parse` 在调用 `graph.addEdge` 时加 try-catch，捕获 `IllegalArgumentException`，转为 `ParseIssue` 加入 `errors`；保证 `parse` 始终返回 `ParseResult`，不抛异常 |
| **备注** | 正常情况下 `containsFormatDelimiter` 已拦住所有 `Vertex` 会拒绝的字符，try-catch 是兜底；契约要求解析失败返回结构化错误列表，不抛异常 |

### 场景 23：名称首尾含 Unicode 空白（如 U+2003）

| 项目 | 内容 |
|---|---|
| **触发条件** | 用户输入 `<\u2003A,B>`、`<A,\u2003B>`、`<\u2003,B>` 等名称首尾含 Unicode 空白（如 U+2003 EM SPACE）的行 |
| **程序应表现** | 先检查非法字符，再 `strip()` 去除首尾空白；`<\u2003A,B>` 与 `<A,B>` 视为同一关系；`<\u2003,B>` 报"起点名称为空" |
| **处理方案** | `DataParser` 和 `InputValidator` 的 `extractPair` 统一处理顺序：先对原始名称检查非法字符，再用 `strip()` 去除首尾空白，最后判断清理后是否为空。与 A 的 `Vertex.normalizeName` 规则保持一致 |
| **备注** | `trim()` 只清除 ASCII 空白，不清除 `U+2003`；`strip()` 清除所有 Unicode 空白。D 使用 `strip()`，与 A 的 `Vertex.normalizeName` 对齐。首尾的 Unicode 行分隔符（`\u2028`、`\u2029`、`\u0085`）会被先检查非法字符后拒绝，见场景 21 |
