# 代码规范草稿

本规范是 A 为 9 月 17 日会议准备的 V0.1 草稿，用于统一五人协作中的基本写法。当前 JDK 21 编译设置已经用于基础工程，但团队兼容环境仍待确认。重点是让接口明确、行为可验证、修改容易合并，不增加与课程目标无关的框架或复杂抽象。

## 命名和目录

包名使用小写，类名使用大驼峰，例如 `Graph`、`TopologicalSolver`，方法与变量使用小驼峰。公开类的 `.java` 文件名与类名一致，因此 Java 源文件不适用旧方案中“文件一律中文命名”的笼统要求。说明文档可以用中文标题，源码统一 UTF-8，缩进使用四个空格。

## 模块边界

`model` 和 `algorithm` 不依赖 Swing，不直接访问文件或弹窗；数据解析与文件读写由 `io` 负责，窗口和调度由 `ui` 负责。`view` 读取 Graph 并维护布局坐标，不把坐标或选中颜色写进算法状态。共享接口改动应同时更新契约并告知受影响的人，不能只改方法名就交给别人解决编译错误。

## 注释和结果

公共类和关键方法添加必要的 Javadoc，说明职责、参数约束、返回结果和异常。算法中解释入度更新、回溯恢复和环路径提取等关键步骤，不给每一行重复写字面注释。每个结果对象都应明确有效条件，尤其区分含环、完整枚举、数量截断、取消和超时。

## 数据与错误处理

算法使用局部状态，不能因一次计算改变原图，返回的结果列表不能与回溯中的可变列表共享。错误在能够解释和处理的层级捕获，底层提供原因，由界面统一显示中文信息；不使用空的 catch 块，也不把所有异常一律伪装成“没有结果”。行号只用于有来源行的解析错误，文件错误和算法状态不强行伪造行号。

## 界面与耗时计算

Swing 组件更新由 B、C 在界面线程中处理，可能较慢的枚举由后台任务调用。A 在计算过程检查取消和运行时限，B 决定按钮状态和提示显示，双方共同保证旧任务结果不会覆盖新输入。具体实现采用最简单满足需求的方式，不在接口尚未确认时铺设复杂线程框架。

## 验证与提交

每次提交前查看差异并运行对应检查，不能只以“能够编译”证明算法正确。排序检查覆盖全部节点和每条边，枚举用可手算的小图核对结果集合，环路径需要验证相邻边真实存在。按有意义的任务提交，保留真实失败和修复依据，不伪造测试通过记录，不修改其他成员的作者信息。
