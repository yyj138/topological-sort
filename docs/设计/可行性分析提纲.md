# 可行性分析报告提纲

本提纲对应 T-A7，供后续撰写正式可行性分析报告，当前不是报告定稿。原方案要求 9 月 20 日初稿、9 月 27 日定稿，正式提交时按课程要求准备 Word 与 PDF。以下区分已知依据与尚需补充的信息，不把计划中的性能和成员能力写成已经验证。

| 章节 | 需要回答的问题 | 当前依据与待补内容 |
| --- | --- | --- |
| 项目目标 | 软件解决什么问题，最少要实现什么 | 桌面 GUI、关系输入与导入、绘图、多序列排序、关系图和结果导出；用任务书示例与课程数据验证 |
| 技术可行性 | Java + Swing 能否实现，难点在哪里 | JDK 包含 Swing；本机已通过基础编译与类加载检查；多结果枚举、布局与后台取消仍需实现和验证 |
| 经济可行性 | 开发和验收需要哪些资源 | 现有电脑、JDK、VS Code 与仓库可作为开发基础；团队是否存在其他资源或许可需求待确认，不预先承诺所有费用为零 |
| 操作与人员可行性 | 五人能否完成各自模块 | 分工已有，具体熟练程度与可投入时间需成员补充；A 不应默认承担所有延期任务 |
| 进度可行性 | 如何在中期及最终期限前交付 | 先确认接口、尽早交出 Graph，再分模块联调；9 月 20 日准备可运行阶段版本 |
| 风险与应对 | 什么可能拖延，如何控制 | 枚举规模、接口歧义、布局工作量、验收环境和文档合稿；逐项明确负责人、限制和验证方式 |

核心风险是合法顺序可能非常多，不能承诺任意图都快速完整枚举。建议先保证小图枚举正确，大图提供明确的上限、取消和时间控制，并记录是否完整。性能结论必须来自实测，记录节点数、边数、数据特点、结果限制和测试环境。

需求范围需与 B 的需求分析保持一致，避免一份文档只承诺基本绘图，另一份却承诺复杂实时交互。人员和数据来源情况应在 9 月 17 日会上补齐，9 月 20 日前形成可用于中期检查的初稿。最终稿根据实际实现修订，不保留未完成的功能宣传或未经验证的测试结论。
